# Feature reference

Everything Mailchat Vault does, in detail: features and their guarantees, first-run
behavior, data locations, media handling, background jobs, export, and per-format
import notes. Setup guides: [AI-assisted search](ai-search.md), [IMAP sync](imap-sync.md),
and [Testing](testing.md). The specification set is indexed in the [docs overview](README.md).

## What the app does

- **Tauri 2 desktop app** (Rust backend, vanilla TypeScript + Vite frontend).
- **SQLite storage with FTS5 full-text index** (bundled SQLite via `rusqlite`; no system SQLite needed).
  - **Canonical store** (schema v14): `source_instances` (durable connector entities: kind, label, non-secret configuration, connected state, per-source exclusion flag, last attempt/success, last sync error), `conversations` (stable provider keys), `archive_messages` (ids, payload, and time provenance: resolved UTC instant, original timestamp text, timezone, confidence), `message_identities` (dedup identities — legacy `(source, external_id)` aliases plus connector-scoped keys with semantic revision hashes), `message_occurrences` (import/folder observations), `import_checkpoints` (bounded-import resume positions), `import_issues` (durable per-item parse failures), `sync_checkpoints` (IMAP cursors), `sync_failed_items` (the IMAP failed-item ledger: what fell, where, why, how often retried), plus the `archive_fts` virtual table (external content, trigger-maintained). Every read and write targets these tables.
  - **Safe migration** (M1.4): opening an existing database with pending migrations first refuses any database written by a newer build (before a single byte is touched), preflights free disk space, snapshots the archive file (`<db>.pre-migrate-v<version>.snapshot`, WAL checkpointed first), converts in **one transaction** (all or nothing), then validates the result (`PRAGMA quick_check` plus full-text-index document-count parity and FTS5 `integrity-check`). Any failure — before, within, or after the conversion — restores the original byte-for-byte from the snapshot; a validated conversion cleans the snapshot up. A failed post-conversion validation additionally records a durable `<db>.migration-failed` marker, so later opens refuse with that recorded reason instead of retrying the same deterministic failure forever — the original stays recoverable from the kept snapshot, and recovery is manual by design (fix or restore the archive, then delete the marker). Proven by failure-injection tests at every stage.
  - **Stable conversation keys**: Telegram/Signal chats key on the provider-guaranteed chat id, WhatsApp chats on a content-derived key (sorted participants + first authored message), and Messenger threads on the thread folder's trailing `_<digits>` suffix, so the same chat re-exported under a rename stays one conversation (the label follows the newest name) while different chats sharing a display name stay distinct (same-titled Messenger threads stay distinct too). **Email reply graph**: `In-Reply-To`/`References` chains group mail into threads — one-hop resolution, so incomplete chains and reference cycles are safe — with replies imported before their roots adopting them into the right thread later. Timestamps carry **explicit timezone interpretation** (exporter-local WhatsApp stamps resolve DST-aware in the machine's IANA zone; Telegram's naive `date` fallback stores the exporter-UTC stamp verbatim; mail offsets and chat epochs are exact) with per-message confidence labels. Legacy databases upgrade in place (migration 7): renamed imports merge, same-name chats split, WhatsApp identities re-key so post-upgrade re-imports dedup, and their legacy blind-Z stamps resolve to stored true UTC instants (machine-zone interpretation), while whatever cannot be safely interpreted stays legacy-unresolved.
  - The legacy `messages` / `messages_fts` / `imap_sync_state` tables from earlier schema versions are preserved untouched as a pre-canonical snapshot; migration 4 copies every row (ids included) into the canonical tables, and nothing writes the legacy tables afterwards. Migration 8 adds the durable source-instance columns (connector identity key, state, attempt/success stamps); migration 9 adds the IMAP failed-item ledger and the per-source exclusion flag; migration 10 adds the bounded-import recovery tables (`import_checkpoints` resume positions, `import_issues` durable per-item parse failures); migration 11 seeds the periodic-sync schedule singleton (`sync_schedule`, M2.4: opt-in flag + interval; runtime deadlines are process-local by design).

  - Trigger-maintained counter tables (`stats_source`/`stats_day`/`stats_chat`/`stats_author`) power the statistics dashboard with O(groups) reads instead of GROUP BY scans.
  - Versioned migrations applied automatically on open — guarded by the safe-migration path above (snapshot, rollback, newer-schema refusal).
- **Idempotent ingest**: a `Source` trait yields messages; writes dedup on the canonical identity — legacy `(source, external_id)` keys map to one `message_identities` row each, and the IMAP connector scopes identities to their durable source instance with a semantic revision hash (the same mail in several folders is one row with one occurrence per folder; two conflicting payloads behind one `Message-ID` are preserved as two revisions) — so re-importing and re-syncing are always safe. Production imports stream through the **bounded parsers (M2.2)**: they never hold a whole archive in memory, parse failures land as durable `import_issues` rows, and an interrupted import (crash or cancel) resumes from its committed checkpoint on the next run — re-importing the same file is always safe.
- **Manual/demo source**: import an `.mbox` file, a bare `.eml` message, a folder of `.eml` files (one level, file-name order), or a `.zip` of `.eml` files — no IMAP needed — subjects, authors, dates, and decoded text bodies are archived and searchable; each mail's MIME attachments/inline parts (M4.2) are decoded (base64/quoted-printable undone) and copied into the content-addressed `media/` store, linked from the message's `media` entries. Every mail pick shares the `mbox` identity namespace, so the same message in a Google Takeout `.mbox` and a loose `.eml` (renamed files are sniffed by content) stores exactly once.
- **Chat imports**: WhatsApp `.txt` exports, Telegram Desktop `result.json` exports, Signal Desktop conversation `.json` exports (e.g. `sigtop export-messages -f json`), Discord Data Package `messages.json` files, Facebook Messenger *Download Your Information* JSON exports, and the app's own JSON Lines `.jsonl` exports (rows keep their original source and external id, so an exported subset lands identically in another vault and re-imports never duplicate) — texts, authors, and timestamps are archived and searchable; quoted replies are kept as metadata, and Signal/Discord attachments are recorded in `raw_json` (Discord reactions too). A picked **`.zip`** works too (WhatsApp export zips, Telegram export zips, Discord Data Package zips, Messenger DYI zips, Signal export zips): it is expanded through the M4.1 import bounds and resolved like a directory pick. **Media extraction** for WhatsApp, Telegram, and Signal (and Messenger tree picks — see the Messenger note below): files referenced by the export (images, documents, voice notes) are copied into a content-addressed `media/` store in app data — hash-named (SHA-256), deduplicated by content — and linked from the message's `raw_json`, with a media section in the detail view. Extraction can be switched off with the **extract media** toggle; text-only exports import fine (each absent file is recorded as an explicit `missing` entry on its message — never silently dropped), re-importing an export with its files backfills media links into already-stored messages, and a whole-tree pick (directory or `.zip`) also stores files no message references — only the media budget running out or the unlinked tree walk failing can leave export files un-stored, and both are counted honestly in the import summary (`unlinked_dropped` / `unlinked_walk_failed`) instead of dropped silently. The format is auto-detected from the file contents, so re-importing the same export never duplicates messages. JSON Lines imports carry no media bytes — `raw_json` media references stay references (the backup container is the whole-vault tool).
- **Drag-and-drop import**: drop export files or folders anywhere on the window — two dashed drop zones advertise the surface (on the first-run **Add your first source** card and in Sources → **Import**, both reading "Drop archives here — .mbox · .eml · .json · .jsonl · .txt") and highlight while a drag is over the window. Each dropped path runs through the exact same bounded **preview → confirm → import** flow as the picker buttons — nothing is stored without the confirmed preview. Several dropped paths preview one at a time in drop order (the waiting count reports in the section's status line), a drop while an import runs waits for it to finish, and drops are ignored while the sample archive is open, exactly like the picker buttons. Routed through the Tauri 2 drag-drop events (real file and folder paths, which webview DOM drop events do not expose) with the window's `dragDropEnabled` setting pinned on.
- **IMAP sync (Gmail & friends)**: incremental, UIDVALIDITY/UID-tracked sync from any IMAP server over host/port/user — Gmail via **Google sign-in (OAuth2 → SASL XOAUTH2)** or **app password**; any other IMAP server via user/password. Folders map to the message `channel` field; re-syncing never duplicates. Each fetched mail's MIME attachments/inline parts are stored into the media store as the sync parses them (M4.2), deduplicated by content across messages, folders, and accounts. Secrets are prompted for or obtained via OAuth, kept in the OS keyring when available and in session memory otherwise — never in the database. The write unit is the **atomic fetch batch** (M2.3): one batch's messages, its failed-item ledger updates, and the checkpoint advance commit in a single transaction, so an interruption mid-folder leaves the checkpoint exactly at the boundary of what is durably stored; items the vault cannot store (unparseable mail, a uid the server searched but never delivered) are recorded in a **durable failed-item ledger** (what fell, where, why, how often retried — visible via `source_failures`) and retried by every later round until they resolve; a `UIDVALIDITY` reset rescans from UID 1, dedups, and clears the abandoned validity's ledger rows in the same commit.
- **Background jobs (M2.1)**: the archive is served by a database pool — one dedicated **writer worker thread** behind a **bounded write queue** plus **two read connections** (WAL) — so searches never wait behind imports, syncs, or embedding runs. Long operations run as **typed background jobs** (queued → running → succeeded/failed/cancelled, with progress events) exposed through the v2 `job_*` IPC commands; misses in the `job-event` event stream are recovered by **polling with a monotonic cursor**. Network work (an IMAP fetch) never runs inside the write lane, a storage lock, or a transaction ([details below](#background-jobs-m21)).
- **IMAP coordinator (M2.3)**: rounds over **every configured IMAP source at once** — the `imap_sync_all` background job (or a coordinator round through the same API) lists the vault's durable source instances, **skips excluded ones** (per-source exclusion keeps the archive and cursors, only pausing the syncing — `source_set_excluded`), resolves each source's credentials from the OS keyring (stored password, else a stored Google sign-in refreshed into a fresh access token; a source without credentials is reported, not errored), and syncs each through the M2.1 pool: network waits on the job thread, atomic batch commits through the write queue — searches and writes keep working while a round is parked on a stalled server. A source that fails syncs alone and carries its error; the others still sync.
- **Periodic sync scheduler (M2.4)**: an **opt-in** auto-sync — off until you turn it on — that runs one coordinator round every interval (**15 minutes by default**; 5/15/30/60 selectable, 1 minute..1 day accepted) as an ordinary `imap_sync_all` job, so scheduled rounds show up in the jobs panel like manual ones. The schedule persists in the vault and re-arms on the next start; it runs while the app process is running — with the opt-in **background keep-alive** (see the M7 bullet below) that spans window closes. Scheduling never overlaps and never queues missed runs: there is one deadline and at most one scheduled round queued or running — a round that outlasts the interval simply delays the next one — and each deadline anchors at the previous *submission*, so sleep/resume/offline gaps collapse into exactly one catch-up round instead of a burst. Disabling cancels a still-running round (cooperatively); enabling arms one full interval out (never an immediate round). Exposed through `sync_schedule_get` / `sync_schedule_set` and the `scheduler-status` event; the toggle lives in Sources → **Automatic imports**.
- **Desktop notifications (new mail after sync/watch)**: when a sync round — the Sync button, a coordinator round, or a scheduled auto-sync round — or a folder-watch import stores **new** messages, the app shows one native OS notification ("2 new messages — INBOX, Archive" / "imported from chat.txt") through the Tauri notification plugin: the same code path on macOS, Windows, and Linux. Notifications stay **silent while the app window is focused** (you are already reading in the app), never fire for a cycle that stored nothing new (skipped/failed/resolved items don't count), are never duplicated when events replay, and can be turned off with the **Desktop notifications** checkbox in Settings (on by default; enabling it asks the OS for permission). A missing permission or unavailable OS notifier degrades silently — the archive data is already safely stored.
- **Background keep-alive (M7)**: two **opt-in, default-off** Settings options extend what the notifications and auto-sync above can do — *keep running in the background* (closing the window hides the app to a **tray icon** instead of exiting, so the opt-in auto-sync schedule, folder watching, and new-mail notifications keep working between opens) and *start automatically at login* (OS login-item registration, applied the moment Settings are saved). While keep-alive is on, the tray menu offers **Show Mailchat Vault**, **Sync now** (an ordinary `imap_sync_all` job — exactly the manual round, visible in the jobs panel), and **Quit**; a **single-instance guard** makes a second launch focus the existing window instead of opening a second app over the same vault. Closing without the toggle behaves exactly as before (the process exits); where the tray icon cannot be built (the appindicator library is missing on Linux, or the tray build fails), keep-alive degrades to that same close-and-exit instead of ever leaving a hidden unreachable process (a desktop that accepts the icon but renders no status area leaves it invisible — recovery is a second launch, which the single-instance guard focuses). The scheduler, coordinator, jobs, and watching layers are untouched — keep-alive only decides whether the process lives between window closes. There is deliberately **no headless daemon/service**: background operation is this tray keep-alive, never a second process over the vault (see the D10 amendment in [decisions](decisions.md)).
- **Folder watching**: pick folders (typed path or the native picker) and every new or modified `.mbox` / `.eml` mail file, WhatsApp `.txt`, Telegram `result.json` / Signal conversation `.json` export, and Messenger `message_*.json` thread part (a part landing re-imports its whole thread) under them is imported automatically in the background — watched folders persist across restarts, write bursts are debounced until a file settles, re-imports never duplicate (the same dedup contract as manual import), and skips/errors are shown in the UI without ever stopping the watcher ([details below](#folder-watching)).
- **Sources screen (every source in one list)**: each configured source — email (IMAP) accounts and file imports (mbox / chat exports) — appears on the **Sources** home with its name, kind, per-source message count (the same trigger-maintained counters the source chips use), last-sync/import stamp, and sync state (open failed-item backlog, the last sync error — what fell, why, when — pause state, and which credentials are stored). Primary row actions: **View messages** (scopes the archive to that source's stable id, keeping the query) and, for email, **Sync now** (re-runs `sync_imap` with the account's stored host/user/folders and an empty password — the backend resolves the keyring secret, password first, else the Google sign-in, exactly the coordinator's precedence). Management actions sit behind each email row's **Details** fold: **Pause/Resume** (the per-source exclusion — auto-sync rounds skip it; archive and cursors kept), **Update credentials…** (the connect form prefilled with the account's identity), **Forget credentials** (removes the password and Google sign-in from the OS keyring; the archive stays), and a two-step **Disconnect…** (exclusion + credential removal in one action — the archived messages always stay; there is deliberately no archive deletion). **Add source…** opens a chooser with exactly two ways in — **Import files…** and **Connect email…** (visible labels, server/port/folders behind an Advanced fold) — and **Automatic imports…** holds the shared auto-sync toggle and folder watching. Sources are derived from the stored source instances + sync cursors — no new tables, no schema break; the per-source stats query is bounded and indexed (one counter row per source).
- **Statistics dashboard**: archive aggregates in one view — total messages and date range, a per-day histogram (auto-downsampled to months/years when the archive spans too many days; bars carry a heat ramp so busy days read without hovering, and first/middle/last bucket labels sit under the chart), and tables with inline bars for messages per source, top chats, and top authors (one categorical color per table, marked by the dot before each heading). Served from trigger-maintained counter tables (schema migration 6), so the whole dashboard answers in **< 100 ms even on 1M messages** (asserted by a generated 1M-fixture test).
- **Workspace layout (M3.1)**: the app is a three-area workspace — **source navigation** (three primary destinations — **Archive**, **Sources**, **Settings** — plus the secondary **Activity** link with an active-job count badge and a "needs attention" flag on failure, and per-source scope chips that select by stable source id), **results** (a **Search / Ask** tab pair over one column — search + filters + pagination + export on the Search tab, natural-language ask with its provider/consent/embedding controls on the Ask tab; both panels stay mounted, so results and answers survive tab switches), and a **reading pane** (full message with thread context) — with independent vertical scrolling. Imports, source management, and maintenance live outside the reading surface in navigation destinations. Visuals come from **local design tokens** (semantic CSS custom properties for canvas/panel/text/border/accent/selection/match/status colors, light + dark + System themes via the existing theme setting) and the **bundled Source Sans 3** variable font (latin + latin-ext + italic, SIL OFL 1.1 — license committed at `src/assets/fonts/OFL.txt`; falls back to native UI fonts, nothing is fetched remotely). **Narrow-window states**: the navigation column is hideable on every width (the topbar hamburger — on desktop it removes the column entirely and the choice is remembered across launches, below 800px it works the drawer); ≥ 1100px shows all three areas side by side; 800–1099px shows navigation + results, and opening a message swaps in the reading view with a visible **Back to results** (query, filters, page, selection, and scroll are preserved); below 800px (including 1280px at 200% zoom) everything collapses into one column behind a labeled **navigation drawer** — no horizontal scrolling. **Accessibility**: semantic landmarks (`nav`/`main`/`aside`), labelled controls, `role=status` live regions announcing search/job/status changes, a skip link, focus moved to the message heading when the reading view swaps in (and restored to the initiating result on Back), and `Ctrl/Cmd+K` or `/` to focus search. The frontend is split into explicit modules: typed **IPC boundary** (`src/ipc.ts`), **state** (`src/state.ts` — layout resolution, the last-request-wins `SequenceGuard` behind every panel's stale-response protection, and the workspace store), and the **shell controller** (`src/workspace.ts`). Layout states are proven by the `16-workspace-layout` e2e spec with committed wide/medium/compact/zoom screenshots (`tests/e2e/fixtures/screenshots/`, synthetic data).
- **Search tool UI** over the FTS5 index:
  - results in a **flat list** (no conversation regrouping) with **match highlighting** (FTS5 snippets, rendered as `<mark>` runs), in **relevance or newest order** (your choice);
  - **filters**: source chips (email/whatsapp/telegram/… — whatever the archive holds), author substring, a from–to date range, an attachments with/without selector, and an import-scope selector (browse one bounded import run); an empty query browses newest-first;
  - **result count + pagination** (`1–50 of 1,234 · page 1/25`);
  - **export**: the current search results — every row under the active filters, all pages, not just the visible one — or a **selection** of the rows you check (as UTF-8 text or JSON with provenance), or the whole chat thread from the detail view, written to a file you pick (native save dialog) as **CSV** (RFC 4180), **JSON Lines** (one full message object per line; the same format the app imports back) or **MBOX** (email rows; non-email rows are skipped and reported);
  - **message detail** (reading pane): full body with highlighted query terms, full metadata, and the **chronological conversation context** around the message — every context row (the opened message and its neighbors) highlights the active query terms with the same `<mark>` runs, capped at the first 50 marked occurrences per message so term-dense bodies stay readable; load earlier/later pages in place; copy, copy link (`mailchat://message/<id>`), and export actions;
  - **keyboard navigation**: `Ctrl/Cmd+K` or `/` focus search, `↑`/`↓` move through results, `Enter` open detail, `↑`/`↓` walk the conversation context, `Esc` close (never erases the query).
- **Media viewing (M4.3)**: preserved image/audio/video attachments render inline in the reading pane through the app's read-only `mcmedia://` protocol — strict hash-named object URLs (`media/<sha256>.<ext>` shapes only), byte ranges, and a hard response CSP; playback is always user-started (no autoplay) and nothing is fetched remotely. Documents and everything else stay explicit rows with **Save a copy…** (byte-exact export via the native save dialog) and **Open externally…** (a disposable 0600 temp copy in a 0700 temp directory is handed to the OS handler — the store object is never touched, only the most recent open's copy survives, and copies are purged again at startup). Settings gains a **Media store** section with a disk-usage report (totals, referenced/orphaned split, per-extension and largest objects) and a Reconcile hash check.
- **Backup & restore (M4.4)**: one versioned `.mcbackup` container holds the whole vault — a consistent SQLite snapshot (taken through SQLite's backup API, never a live-file copy), the settings file, and every referenced media object, each entry checksummed in a manifest written last. Restoring is staged and journaled: the container is re-checksummed and its database validated (integrity, foreign keys, schema ceiling, object presence) in a staging vault outside the active one, the commit re-verifies the staged bytes and refuses a vault that changed since the preview, and the switch itself runs through a two-phase journal (crash → rollback or roll-forward to one verified whole vault, recovered automatically at startup). The replaced vault is always kept as a previous-vault snapshot (Settings → Storage & backup lists them; return to one or explicitly forget it). Passwords and API keys are never backed up or restored — only accounts whose credentials are missing from this machine's keyring need reconnecting after a restore (a same-machine restore with live keyring entries asks for nothing).
- **Performance contract**: queries answer in < 100 ms over 100k messages (asserted by a generated-fixture test; all queries are `LIMIT`-bounded and ride the FTS5 index plus the `sent_instant`/`(source_instance, chat_id)` indexes); the statistics dashboard answers in < 100 ms over 1M messages.
- **Ask UI (v1)**: natural-language questions translated to FTS5 + date filters via an LLM, with a short summary over the top results — strictly privacy-scoped, **consent-gated** (M5: nothing leaves the machine without an explicit, session-scoped agreement), and fully optional ([AI-assisted search](ai-search.md)). Results are ranked **hybrid** — FTS5 fused with an offline local-vector leg once embeddings are built ([local embeddings](ai-search.md#local-embeddings--hybrid-search-v1)). A **provider menu** next to the question picks the backend per ask: any provider configured in Settings, the environment fallback, or **local full-text** (nothing sent anywhere). **Answers are source-linked** (M5): citations `[1]`, `[2]`, … in the answer are clickable, as are the numbered result rows beneath — either opens the original archived message in its conversation context in the reading pane.
- **Settings (three pages)**: **General** (UI theme, desktop notifications, the M7 background keep-alive toggles), **Storage & backup** (the M4.4 backup/restore + previous-vault recovery and the Media store report — loaded only when that page opens), and **AI assistance** (LLM provider configuration — z.ai/GLM (default), Anthropic, or a custom Anthropic-compatible endpoint — plus the default provider and summary scope); each page has its own Save that persists the whole form. Values live in a `settings.json` file (never the database); API keys live in the OS keyring ([Settings](ai-search.md#settings-screen)).

## First-run tour

First run tip: an empty archive opens on **Add your first source** — click **Import file…** (or **Import folder…** for a Telegram export folder / Discord Data Package) and pick any `.mbox` or `.eml` file (e.g. exported from Thunderbird), a WhatsApp `Export chat` `.txt`, a Telegram export's `result.json`, a Signal conversation `.json`, a Discord Data Package export, a Messenger (Facebook) JSON export, or a JSON Lines `.jsonl` file exported from any vault — or just drag the file (or a whole export folder) onto the window, which routes through the same flow; everything shows a bounded **preview** (format, samples, counts, media presence, size) before anything is stored, and **View imported messages** jumps to what the run brought in. Not ready with your own data? **Try a sample archive** — an isolated in-memory demo (search e.g. `vault`, click a hit to read it in context) that never touches your vault; leave it and your archive is exactly as it was. The workspace also browses newest-first on its own (**All messages**), so a fresh import is visible without typing anything. Click **Update local embeddings** in the Ask section to build the local vector index (offline) — Ask then ranks results hybrid (FTS + local vectors). To take results out, run a search and press **Export results…** (or open a message and press **Export chat…**), pick a format and a destination — the export always covers every row of the current search, not just the page on screen.

## Where the data lives

The database lives in your app data dir (e.g. `~/.local/share/com.acailic.mailchatvault/vault.db` on Linux); extracted chat media lives next to it under `media/`, each file named by the SHA-256 of its contents.

## Media store lifecycle & integrity (M4.1)

Objects are written through an explicit **stage → promote → reference** lifecycle: bytes stream into `media/.staging/` while being hashed and budget-checked, an atomic rename promotes them to `media/<sha256>.<ext>` (never a half-written object in the objects area), and only then does the ingest commit record the digest in the message's `raw_json` — so a crash at any point leaves at worst invisible staging litter (swept later) or a harmless orphan the next import dedups onto, never a dangling reference. Every import tree — a directory walk or a ZIP expansion — goes through the same **import bounds**: `..`/absolute/backslash traversal and symlink escapes are refused, symlink entries never extract, and file-count/byte/depth budgets bound runaway input. Objects are byte-exact copies of their inputs (input-original preservation); the `media_reconcile` command is the integrity tool — it re-hashes the store against every referenced digest and reports missing references, orphans, corruption, staging litter, and foreign files (a clean import reports zero of everything).

## Media references, missing states & re-import enrichment (M4.2)

Every reference a message carries becomes one `media` entry in its `raw_json` — a stored one (`sha256`, `path`, `name`, `kind`, `size`) or an explicit **missing** one (`missing: true` with a reason, `not-in-export`, `unreadable`, or `budget-exceeded`), so the archive never silently drops a reference it could not preserve; the detail view shows missing entries as unavailable attachments rather than as a gap. Email attachments — `.mbox` import and IMAP sync alike — are MIME-decoded by the parser (any `attachment` disposition, an inline part with a `filename`/`name`/`Content-ID`, or a non-`text/*` leaf; the message's own text bodies never count) and staged through the M4.1 lifecycle before their batch commits. A **whole-tree pick** (a directory, or a `.zip` that expands into one) additionally stores files no message references and registers them in the `media_objects` registry — countable by reconciliation as referenced, listable through the vault-core `unlinked_media_objects` library API (the app UI surfaces it in the media-display milestone) — while a bare export file never reaches beyond its own references. Re-importing the same export enriches instead of duplicating: identical bytes hash to the same object (dedup across names, messages, and imports), an already-linked message gains nothing twice, a missing entry is upgraded in place when the bytes finally arrive, and repeated missing markers for the same name are not stacked. Opening a stored object (today a vault-core library API, `resolve_object`; the app UI surfaces it in the media-display milestone) resolves strictly inside the store — it accepts exactly one `<sha256>.<ext>` object name, refusing traversal, sibling names, and anything that is not a stored digest.

## Folder watching

The **Folder watching** section turns the archive into a live mirror of your
export folders: type a path (or use **Pick folder…**) and every new or
modified `.mbox` or `.eml` mail file, WhatsApp `.txt`, Telegram
`result.json`, Signal conversation `.json`, or Messenger `message_*.json`
thread part under it — including files inside subfolders — is imported in
the background. A Messenger part landing means its *thread* changed, so the
whole thread is the import unit: part 2 arriving re-imports the thread and
every message stores exactly once.

- **Debounced**: files being written or copied fire many filesystem events;
  a file is imported only once it has stayed quiet for ~1.5 s. A truncated
  read self-heals: the next modification re-imports the file and dedup keeps
  the archive consistent.
- **Dedup by contract**: imports go through the ordinary ingest pipeline, so
  `(source, external_id)` uniqueness makes every re-import safe — the initial
  scan of a folder, re-settling, and rewrites of a file all store each message
  exactly once.
- **Never fatal**: unreadable files, unknown formats (reported as *skipped*),
  and database hiccups are recorded in the events list; the watcher keeps
  running. A folder that vanishes mid-session is silently disarmed for the
  session. Skipped files with a watched extension (`.mbox`/`.eml`/`.txt`/
  `.json`) that are not recognized exports are reported, not imported.
- **Persistent**: watched folders are stored in the vault database and
  re-armed on the next start (a folder that is missing at startup is
  reported; it re-arms on the next start once it is present again).

The status line shows how many folders are watched and how many files are
still settling; the events list below shows folder add/removals, imports
(with new/duplicate counts), skips, and errors. A background import
refreshes the source chips and stats like any manual import.

## Background jobs (M2.1)

Since M2.1 the app never serves the archive through one guarded
connection. Instead, a **database pool** opens the vault file through
several SQLite connections in WAL mode — each one initialized with the
same pragmas and custom functions — and splits the work:

- a **writer worker thread** owns the one write connection. Writes are
closures submitted over a **bounded queue** (capacity-bounded: backpressure
instead of unbounded memory, one writer instead of lock contention), and
submitters wait for their result — the v1 commands keep their synchronous
IPC shape while gaining the pool's guarantees.
- **two read connections** serve searches, stats, dashboard reads, and
exports; two readers may work at once, and WAL means none of them ever
waits for a commit.
- a **job runner thread** executes long operations (the v2 background
jobs: `embed_messages`, `import_mbox`, `import_chat_export`,
`imap_sync`, `imap_sync_all`, `seed_demo`). A job never holds a
connection: its reads and
writes round-trip the pool, so waiting on the IMAP server — or embedding
a large archive — occupies neither the write lane nor a read slot.
 **No network operation runs inside the writer, a storage lock, or a
transaction**: the IMAP sync (`SyncStorage` + the `PoolSync` adapter)
fetched on its own thread between write round-trips, proven by a test
that parks the mock server mid-fetch and completes a write + a search
while the fetch is stalled. `imap_sync_all` (M2.3) runs the coordinator
round — one source at a time, each with the same atomic batch commits
and the same stall proof at round scale.

Jobs carry **typed states** (`queued` → `running` → `succeeded` /
`failed` / `cancelled`, the latter with typed error kinds: `storage`, `io`,
`import`, `network`, `cancelled`, `queue_full`, `invalid`, `internal`) and report
**progress** (the embedding job, per batch). Every state change appends
an event stamped with a global
monotonic `seq`; the shell emits each one as a `job-event` window event,
and the UI keeps a cursor. **Missed events are recoverable by polling**:
`job_events_since(cursor)` returns exactly the gap plus a fresh job
snapshot, and a `trimmed` flag tells the client the bounded event ring
no longer holds part of the gap — it then reconciles from the snapshot.
The same poll at cursor 0 is the boot recovery after a webview reload.
Cancellation is cooperative (`job_cancel` sets a flag the job checks at
safe points). The **Background jobs** panel in the UI renders the active
and recent jobs with progress; the *Update local embeddings* button now
submits its work through this protocol.

## Export

The **Export results…** control writes the current search results — every row matching the active text + source/author/date filters, across all pages, in the order the UI lists them — to a file you choose. **Export chat…** (in the message detail panel) writes the whole chat thread of the open message, oldest → newest; a message with no thread exports as a single row. Formats:

- **CSV** — RFC 4180 (`source,external_id,channel,chat_id,author,sent_at,body,raw_json`), UTF-8, fields quoted only when needed; cells beginning with `=`, `+`, `-` or `@` get an apostrophe prefix so spreadsheet apps cannot execute them as formulas.
- **JSON Lines** — one complete message object per line (`.jsonl`); the exact shape the app stores, and the shape the app imports back: picking a `.jsonl` runs it through the ordinary bounded import, every row keeping its original source and external id, so exported subsets move between vaults and re-imports never duplicate (malformed lines become per-item issue records; media references in `raw_json` stay references — media bytes are not transferred, the backup container remains the whole-vault tool).
- **MBOX** — classic `From `-separated mailbox rebuilt from the stored row plus its recorded headers (`Message-ID`, `From`, `To`, `Subject`, `Date`); carries email-channel rows only, chat rows are skipped and reported in the status line.

Rows stream straight to the file, so exports of very large result sets don't hold the whole set in memory.

## Notes on chat import details

- **WhatsApp**: export dates carry no UTC offset, so they are interpreted DST-aware in the machine's IANA zone and stored with the resolved UTC instant plus timezone/confidence provenance (a stamp inside a DST gap stays unresolved with the verbatim stamp kept); day-first vs month-first ordering is inferred from the file's own dates (day-first when ambiguous). Media placeholders (`image omitted`, `(file attached)`, …) are kept as text and recorded in `raw_json`; when the exported files sit next to the `.txt` ("Attach Media" export, unzipped), named attachments are matched by file name — case-insensitive full name first, then by stem (for export flavors that re-encode extensions, e.g. `IMG-1.jpg` shipped as `IMG-1.jpeg`) — and copied into the media store, linked from `raw_json` (`media` array). `<Media omitted>` placeholders carry no name and stay placeholders.
- **Telegram**: `date_unixtime` is preferred for timestamps (timezone-correct); service entries (calls, joins) are skipped; the original message JSON (attachments, reply references included) is kept verbatim in `raw_json`, and `photo`/`file` paths are resolved inside the export directory (`..` and symlink escapes are rejected), stored hash-named, and linked via the added `media` array.
- **Signal**: conversation exports are top-level JSON arrays of Signal Desktop's raw message objects (as written by `sigtop export-messages -f json`, one file per conversation). Timestamps (`sent_at`/`timestamp`/`received_at`) are absolute epoch milliseconds, stored as exact UTC; outgoing messages are archived with author `You`; service entries (call history, key changes, profile changes, group changes) are skipped; message ids are namespaced by the conversation uuid, so a re-export under a renamed file dedups instead of duplicating; the whole original message object (attachments, quotes, reactions) is kept verbatim in `raw_json` — named attachment files (`fileName`) are matched against the export tree by name (full name case-insensitively, then stem, the WhatsApp rule) and stored by the media pass; name-less entries (voice notes) carry no file name a tree file could answer for and stay recorded as references only.
- **Discord**: the Data Package (Settings → Privacy & Safety → Request Data) stores one `messages.json` per channel under `messages/`; pick the package root, the `messages/` directory, or any single channel file. Timestamps carry an explicit UTC offset and are normalized to UTC; `chat_id` is `guild/channel` for server channels and the `index.json` path (e.g. `Direct Messages/@friend`) for DMs; system entries (joins, pins, calls) are skipped while replies are kept; the original message JSON (reactions, attachment info, edits, mentions included) is kept verbatim in `raw_json`. Message ids are snowflakes namespaced by channel id, so re-importing a renamed channel never duplicates.
- **Messenger**: Facebook's *Download Your Information* export with **Format set to JSON** (the HTML flavor is out of scope) writes `messages/inbox/<thread>/message_1.json`, `message_2.json`, … per thread; pick a single thread file, a thread folder, any directory above them (the export root, `messages/`, `messages/inbox/`), or a `.zip` of any of those, and one thread's parts merge in numeric order (`message_2` before `message_10`). Conversation keys come from the thread folder's trailing `_<digits>` suffix — the same thread re-exported or renamed stays one conversation, same-titled threads stay distinct — with the display label taken from the export's `title`, else the participant list. Timestamps (`timestamp_ms`) are exact UTC; the original message objects (photos, shares, reactions) are kept verbatim in `raw_json`, and messages carry synthetic ids (Facebook exports none), so re-imports never duplicate. One unreadable or unparseable `message_*.json` part never costs the pick — the same skip-and-record rule a broken `.eml` gets in a folder: the part becomes one import issue naming the file (counted in the run's failed count, visible in the import's issue list), every healthy thread and part still imports, and a thread whose every part is broken is a single issue naming its first part; fixing the file and re-importing brings its messages in without duplicates. Only structural refusals fail the pick — a picked directory with no thread folders, an unreadable directory — and those errors name the offending path. Media is extracted for tree picks — references resolved against the DYI root, with re-import backfill — while a single-file pick keeps its references in `raw_json` only: a lone file says nothing about the tree around it.
- **JSON Lines** (`.jsonl`): the app's own export format, imported back row by row. Each line is one complete stored message object; the row's exported `id` is ignored while its `source` and `external_id` are kept verbatim, so a file exported from one vault lands identically in another and importing the same file twice stores each message exactly once. Mixed-source files keep their rows under their original namespaces (the run summary itself reports under `jsonl`); malformed lines become durable per-item issue records instead of aborting the run; media references in a row's `raw_json` stay references — no media pass runs, media bytes are not transferred (the backup container is the whole-vault tool).
