## Product idea and existing plans

The repository already demonstrates a useful product: bring private mail and chat exports into one local searchable archive, then optionally ask natural-language questions. Its strongest asset is the shared Rust storage/parsing layer with a small desktop shell, rather than dependence on a hosted service.

The root [README](../README.md) is the existing product description. This `docs/` planning set was authored against the pre-roadmap baseline, reviewed on the `core-archive-v2` branch, and lands on `main` with the M1 slice documented. Since the planning baseline, the roadmap has been executed slice by slice: M1 (identity, provenance, time, safe migration) and M2 (jobs, responsive storage, resumable operations, performance evidence) are complete and verified below; M3.1–M3.2 (workspace, v2 search) have landed as code and their evidence is recorded in the [M3 progress record](implementation-roadmap.md#completion-tracking) (M3.3/M3.4 remain open); M5's consent-gate and source-linked-answer halves are implemented with their evidence recorded in the [M5 progress record](implementation-roadmap.md#completion-tracking) (the M5.1 persisted consent switch and M5.2 job-backed approval flow remain open); M4.1 (object store) and M6.3 (Linux distributions) have landed as code and are recorded in the inventory; their acceptance records remain open until each slice records its evidence.

The next product step remains turning several working controls into one dependable archive workflow: imports with preview/confirmation, preserved media, backup/restore, and the three-platform release.

## Remaining gaps after M2

Implemented corrections versus what M1/M2/M3.1–M3.2 deliberately leave open (design or partial code exists, the rest does not). The M1 list still stands in full; M2's and M3's honest leftovers follow it.

- **Discord conversations** still group by display name (stable channel id dedups messages, but no provider conversation key is derived). Telegram/Signal/WhatsApp/email are keyed.
- **Legacy namespace → account binding**: `user_linked` confidence and explicit binding are designed; no command or UI exists yet, and legacy IMAP namespaces stay unresolved rather than silently attached.
- **`user_confirmed` time confidence**: the label exists in the schema; the import-time date/timezone confirmation flow that sets it is M3.3.
- **Persisted workspace timezone**: v2 search accepts an explicit per-request IANA timezone (OS default when empty); saving a workspace default is designed, not implemented.
- **Cross-export WhatsApp ambiguity** (“match existing” vs “keep additional copies”) awaits the M3.3 preview/confirmation flow; today's behavior dedups exact re-imports and preserves same-export repeats.
- **Legacy snapshot removal** is deferred until recovery and upgrade experience justify a separate migration.

M2 leftovers (from the [completion record](implementation-roadmap.md#completion-tracking)): job records are per-process — no persisted job history, `interrupted`/`partial` states, or linked retries after an app restart (checkpoints/ledgers carry the recovery); all background jobs serialize on one runner thread; cancellation latency is unmeasured (cooperative, bounded by the current batch/socket call); the scheduler drives IMAP rounds only; v2-surface and webview-hop performance remain unmeasured.

M3.1/M3.2 leftovers (from the [M3 progress record](implementation-roadmap.md#completion-tracking)): the v1 render module stays active for unmigrated panels (M3-exit removal pending); per-source status text and account pages await M3.4; Settings holds theme + AI providers only (Storage & backup is M4.4); the workspace timezone is not persisted (per-request, OS default); selection export is a direct command, not a job; the import surface is still the pre-M3.3 interim (typed-path mbox, no preview/confirmation/sample vault/capacity check); the human UX/accessibility sessions (NVDA/VoiceOver, measured contrast, five-user tasks) remain unrecorded.

M5 leftovers (from the [M5 progress record](implementation-roadmap.md#completion-tracking)): the consent switch is session-scoped in-memory only — the persisted off-by-default switch remains proposed until the product owner adopts session-scoped consent as final; asks are direct commands, not jobs (no job record, no in-flight cancellation, no progress — a stalled provider is bounded only by the 30-second timeout); no exact-preview/digest-bound approval and no invalidation on question/filter/result changes (a granted session consent covers the session); asks do not intersect the active workspace filters; the visible unsupported-citation note and the “Based on N matching messages” evidence-scope caption are unimplemented; author metadata in the summary payload is uncapped (only the 500-character body cap is enforced).

## UX critique

The page does not rely on decorative gradients or excessive dashboard cards. Its weakness is product hierarchy: it reads as a collection of developer controls. The most important task, finding and reading a past exchange, competes with provider status, import fields, and server configuration.

What works: search is visible, message text is safely rendered, filtering is direct, and keyboard shortcuts exist. The largest improvement is a persistent archive workspace with imports and account setup behind source management. Reading context should show a human conversation name and participants before technical IDs. The M3.1 workspace layout landed (navigation/results/reading areas, background-jobs panel as Activity, source-failure views as durable progress/issue destinations) and the M3.2 flat results/reading pane landed with honest unknown-time and unverified-grouping presentation; the automated layout/a11y checks are recorded in the [M3 progress record](implementation-roadmap.md#completion-tracking), while the human UX/accessibility session evidence is still pending (see F07).

This critique is based on HTML/CSS and event/rendering code plus the landed workspace modules; browser visual inspection did not succeed at the planning baseline, and no screenshot-based layout or contrast verdict is claimed here.

## Recommended order

Identity and provenance are corrected and recorded (M1), as are jobs, responsiveness, resumability, and the core-path performance evidence (M2), the workspace/v2-search halves of M3 (M3.1/M3.2), and the AI consent/citation halves of M5. Next: deliver the M3.3 import-preview and M3.4 account-management slices with their UX/accessibility session evidence, then media preservation and backup/restore (M4.2–M4.4), then the M5 remainders (the persisted consent switch decision and the job-backed digest-bound approval — M5.1/M5.2), then the three-platform release matrix (M6.1/M6.2). Avoid a framework rewrite, a new hosted backend, or more connectors before these foundations are reliable.
