## Current compatibility boundary

**Current.** Frontend types are in [src/types.ts](../src/types.ts) and [src/v2types.ts](../src/v2types.ts), Rust query types in [query.rs](../crates/vault-core/src/query.rs) / [search2.rs](../crates/vault-core/src/search2.rs), and commands in [the Tauri shell](../src-tauri/src/lib.rs). The legacy v1 command surface keeps its shapes and now runs entirely over the canonical tables — since M1.1 the core storage APIs read and write canonical tables only, so the existing IPC adapters followed without dual writes; the v1 `llm_ask` command carries the M5 AI-consent gate (`consent: true` is the only way any provider round trip happens; see [the AI retrieval contract](#search-request-and-response)). A v2 IPC surface ships alongside: the background-job protocol (M2.1) and the v2 reading surface (M3.2 — `search_archive_v2`, `message_detail_v2`, `conversation_context_v2`, `list_import_scopes_v2`, `export_messages_v2`), which return structured `AppError` results, plus the read-only `media_reconcile` object-store integrity report (M4.1 — it returns string errors rather than the structured `AppError` envelope) and its resolved-detail companion `media_reconcile_detail` (missing/corrupt findings resolved to affected message references and unlinked-file import provenance, paged with totals); the frontend crosses both only through the typed boundary in [ipc.ts](../src/ipc.ts). Legacy message row IDs are stable and unchanged. Do not mix v1 and v2 result shapes under one command name; retire v1 commands only after every repository caller migrates. There are no documented external IPC clients.

## Domain and persistence model

**Current** (migration ledger at schema version 21; 14 is the account-level sync error state on `source_instances` — the restart-durable record of what fell and why — 15 the covering index behind the per-source mail-vs-chat channel probes, 16 the finished-jobs ledger that keeps Activity's history across restarts, 17 the drop of the single-column `idx_archive_messages_source` that 15's composite made redundant, 18 the `saved_searches` table holding the Archive workspace's saved-search definitions as dynamic v2 search requests, 19 the vault-local collections organization layer, 20 the people / user-confirmed identity-link tables of the unified-person slice, and 21 the what's-new boot digest's created_at index (renumbered from its original 20 for the merge — see the note in [Migration and recovery](#migration-and-recovery)) — see [Migration and recovery](#migration-and-recovery)). UUID strings identify durable entities except messages, which keep plain SQLite integer rowids with no guard at JavaScript's 2^53 safe-integer boundary (proposed for the v2 IPC surface: new inserts reject numeric ID overflow rather than rounding it in IPC). Timestamps are stored as UTC instants when known, plus separate original-local/time-confidence metadata.
The following are the logical table contracts as implemented; migrations and indexes live in the versioned ledger in [storage.rs](../crates/vault-core/src/storage.rs).

| `sync_schedule` | **Current** (M2.4): the singleton periodic-sync schedule — opt-in flag and clamped interval only; runtime deadlines and the active round are process-local by design (missed time cannot queue missed rounds) |
| `reminder_preferences` | **Current** (migration 25, A9): one row per source the user opted into manual-export reminders — `enabled`, `interval_ms` (default monthly), the single `next_due_at` deadline (RFC 3339 UTC), and `snoozed_until`. Device-local and content-free by construction: scheduling facts only, no message content. Dismissal is a transition (advance `next_due_at`, clear the snooze), not a column. No row = no reminders; nothing runs after Quit — a deadline that passes while the app is closed is simply due at the next launch, one reminder per source (a single instant cannot queue missed ones) |

| `person_link_history` | **Current** (migration 23, A5a): the audit ledger behind the preview/commit cycle — one row per link/unlink a `person_links_commit` actually applied, carrying the anchor columns, the operation, and the organization revision the commit produced. `person_id` deliberately carries no foreign key: deleting a person removes organization only, and the ledger survives as the record of what was organized. No message payload is derivable from or rewritten by it |
| `settings` | **Mixed**: the persisted `sync_schedule` lives in the vault table above (M2.4), and the non-secret settings file (described in the root README) carries the provider profiles and options including the M6-era `notifications` flag (on by default, serde default, no schema involvement — #59) and the M7 keep-alive flags `keep_running_in_background` / `start_at_login` (strictly opt-in, serde default off, no schema involvement); the versioned UI/timezone/capacity configuration remains **proposed** — the once-proposed AI-consent configuration (the persisted off-by-default switch) is superseded by the 2026-11-16 decision ([#181](https://github.com/acailic/mailchat-vault/issues/181)): consent is session-scoped and never persisted, so no consent setting will be added |
| `archive_meta` | Small key/value table; `archive_revision` increments atomically inside every content-changing transaction so paged searches can detect archive changes under pagination. `last_verified_backup` (U05) holds the persisted record of the last backup a `backup_create` run verified — written after the container finished verifying, read by the Storage & backup panel at boot so the vault's safety state survives restarts; because it rides `vault.db`, a restore replaces it with the restored vault's own history |
| `collections` / `collection_members` | **Current** (part 1 of the collections slice, migration 19): vault-local organization — a named collection references canonical messages across source instances by their stable `archive_messages` rowid. Additive metadata only: message text, timestamps, provenance, and conversation identity remain evidence of the source and are never copied into organization rows. One message may belong to many collections (and one collection holds messages from many sources); memberships are idempotent on `(collection, message)`. `collection_members.message_id` carries **no** foreign key by design: a membership whose canonical message is absent surfaces in the collection detail as an *unavailable* row (reference kept, provenance absent, never fabricated) instead of vanishing. Deleting a collection removes its memberships only — never archived content; collection writes do not bump `archive_revision` (organization is not archive content). Tags and notes are later parts of the slice |

`archive_fts` is an external-content FTS5 index over message body, author, and subject, maintained by triggers on `archive_messages`. It is rebuilt after bulk enrichment (e.g. media backfills). Raw JSON, credentials, file bytes, and hidden source configuration are never indexed. Search-ordered indexes cover source/time/message ID and conversation/time/message ID; occurrence folder membership and identity lookups are indexed. Benchmark query plans instead of assuming indexes eliminate broad FTS ranking costs.

The canonical v2 message table is new relative to the legacy `UNIQUE(source, external_id)` constraint: migration 4 copied existing IDs and payloads into `archive_messages` and retained the old `messages`, `messages_fts`, and `imap_sync_state` tables as an untouched legacy snapshot for this release. All application commands and core APIs use the canonical tables, with no dual writes. Old-schema-version tests remain; current-schema SQL assertions target the canonical store. The temporary disk duplication (old data, new data, FTS, pre-migration snapshot) belongs in capacity estimates. Removing the legacy snapshot is deferred until the recovery and upgrade experience justifies a separate migration.

## Identity and deduplication

**Current.**

**Source instances.** A file import uses an explicitly chosen or created source collection (its source string is the legacy namespace). IMAP identity is a durable source instance keyed by a canonical connector key — kind, trimmed case-folded host, port, TLS mode, and the exact username (`imap\|host\|port\|tls\|username`). Hostnames are case-folded; usernames are not. The password is never part of the key or the stored config (it stays in the OS keyring), so reconfiguring credentials preserves source identity, and two accounts on different hosts remain distinct instances even with the same username. Legacy namespaces are never silently bound to a configured account: binding a legacy collection to a verified account is an explicit user action (**proposed**, the `user_linked` confidence exists in the schema for it).

**JSON Lines exports (portable source identity).** Every JSON Lines export row — search-result exports and whole-conversation chat exports alike — carries a `source_key` next to its display `source`: the exporting instance's label-independent identity — `instance:<kind>:<connector_key>` for connector-owned instances (the `instance:` prefix keeps a machine key from ever aliasing a human label), the legacy namespace for legacy instances. The importer dedups on `(source_key, external_id)` and names the created destination instance after the row's display `source`, so a subset exported from two same-labelled sources round-trips without collapsing rows that share an external id; destination instances are legacy-style under those keys, so re-export emits the same keys and the cycle is stable, and renaming a display label changes only the label. Rows without a `source_key` (every pre-contract export) keep importing under the documented `(source, external_id)` contract. Remaining subset-export fidelity limits: media entries in `raw_json` are references without bytes (no media pass runs on JSONL import), and the exported `id` is the exporting vault's autoincrement — ignored on import, never a stable handle.

**Mail messages (connector-scoped).** Within a source instance, the normalized `Message-ID` (trimmed, angle brackets stripped) is the external key; without one, the SHA-256 of the raw message bytes is the fallback key. A semantic revision hash is computed over decoded content and stable headers (`Message-ID`, `Subject`, `From`, `To`, the original `Date` text, and the decoded body, U+001F-joined); transport-added headers and folder state never enter it, so the same mail re-fetched from another folder or re-encoded in transit hashes identically. The full identity tuple (instance, namespace, external key, revision hash) deduplicates: an exact repeat records only an occurrence (folder, UID, UIDVALIDITY); genuinely different decoded payloads sharing a `Message-ID` become distinct preserved revisions — both archived, both searchable, flagged at insert time (`FolderSyncSummary.conflicting_revisions`) and inspectable through `message_revisions` / `message_occurrences`. Each folder summary also carries the media pass's own counters (`FolderSyncSummary.media`: stored/deduped/missing, `None` when the sync ran without a media pass), filled from the shared `MailMedia` handle's per-folder delta so attachment honesty reaches the sync status line. Cross-source automatic merging is not part of this release; a copied mail from another collection remains a separate archived record.

**Telegram.** External id is `<chat-id>/<message-id>` when the export carries the provider chat id; within a source instance this identifies a message, and exact repeat imports dedup. Display names never determine identity — the conversation is keyed `telegram:chat:<id>`, so a re-export under a rename lands in the same conversation (the label follows the newest name) while different chats sharing a display name stay distinct. Exports without a stable chat id stay on the legacy display-name grouping (legacy-unresolved). **Proposed**: explicit user linking for such exports instead of automatic display-name matching.

**Signal.** The provider-guaranteed conversation UUID is the stable identity: external id `<conversationId>/<id>`, conversation key `signal:chat:<uuid>`. Renamed export files re-dedup into the same conversation.

**WhatsApp.** The format has no message ids. The conversation key is a SHA-256 over the sorted distinct authors plus the first authored message (length-prefixed field join), so the chat survives file renames and re-exports; when no authored message exists, no key can be derived and the legacy stem grouping applies. The external id is a content hash over the conversation key (or stem), author, naive timestamp text, and body, plus an occurrence counter — identical back-to-back messages in one export remain distinct rows, while re-importing the same export (under any name, when a key was derived) dedups everything. The stored identity never changes with timezone corrections: naive exporter-local stamps resolve DST-aware in the machine's IANA zone (ambiguous fold times take the first occurrence; gap wall-times stay unresolved with their original text). **Proposed**: cross-export ambiguity handling (“match existing” vs “keep additional copies”) through the import preview (M3.3).

**Discord.** Dedup follows the stable channel id (fallback: the file stem); display grouping prefers guild/channel names. Provider conversation keys are not yet derived for Discord — grouping is the legacy chat grouping (see [assessment gaps](internal/project-assessment.md)).

**Conversations (email).** Email builds a source-scoped reply graph from `In-Reply-To` plus `References` (root-most first). Resolution is one hop at a time, never a traversal, so incomplete chains and reference cycles cannot loop: the first stored reference that already has a conversation wins (a reply cross-linking two threads lands in the first-seen root-most thread); otherwise the conversation is keyed `email:thread:<root-most ref>`. Stored messages referenced by later replies but still conversationless (a parent imported before M1.3, a root that arrived alone) are adopted into the resolved thread when a later reply reaches them. Never merge by subject alone; mail without reply evidence stays standalone. Referenced-but-absent parents are not fabricated.

**Occurrences.** One mail message can have multiple folder occurrences (scope = folder, provider item = UID, UIDVALIDITY per epoch) and multiple import observations. Remote deletion marks an occurrence no longer observed only on explicit reconciliation; it never deletes archived content. A UIDVALIDITY reset starts a new epoch: the folder is rescanned and re-fetched messages dedup through the connector identity, so a reset never creates duplicate rows. Adding a missing attachment enriches a message without duplicating it. Conflicts and revisions remain inspectable; default search shows all preserved revisions with a conflict marker rather than silently choosing one.

### People and identity links

**Current** (migration 20; storage layer). The unified person view is built on explicit, reversible, user-confirmed associations — never on inference:

- **No automatic linking.** A shared display name is never evidence of identity. Nothing links two author identities unless the user calls the link API; two unrelated people with the same display name stay separate forever unless the user explicitly assigns the same anchor to both (and a single anchor can only belong to one person at a time).
- **The anchoring model.** A link anchors to a canonical `source_instance_id` plus one of: a `stable_key` — a stable, source-scoped author key where the source provides one (an email address for mail sources, a provider user id for chat exports that carry one); or an `author_name` — the verbatim author string where the source provides nothing stable. `author_name` anchors are inherently ambiguous (two humans can share a display name within one source) and are scoped to their source instance exactly to keep that ambiguity bounded. Matching display names across sources never collide: the source instance is part of the anchor tuple. `stable_key` values are case-folded at link time; `author_name` values are stored verbatim.
- **Associations are separate from archived content.** Links live in their own tables; authors, messages, and conversations are never rewritten, merged, or re-attributed. New imports under an already-linked stable key resolve to the person through the anchor — no re-confirmation needed — while the archived rows keep their original author strings and provenance.
- **One identity, one person.** The anchor tuple is unique across `person_identity_links`. Linking an anchor that already belongs to another person is refused with an explanation naming the current owner; resolving a conflict is always an explicit unlink-then-link, never a silent move.
- **Reversibility.** Unlinking removes exactly the association row; deleting a person cascades its links and nothing else. Archived content is byte-for-byte unaffected in every direction.
- **Preview/commit with an organization revision** (A5a, migration 23). `person_link_preview(ops)` reports per-identity evidence — the anchor exactly as stored, matched-message counts in its source instance, up to three representative messages, and a conflict forecast naming any current owner — plus the organization revision it was read at; it writes nothing. `person_links_commit(expected_revision, ops)` applies the set in one transaction: a commit whose revision is not current is refused with the current one (`PersonLinksStaleRevision`) so the caller re-previews, and any refusal (a conflicting anchor, an unknown person or link) rolls back the whole set. Every changing commit writes its `person_link_history` rows and bumps the `organization_revision` counter in `archive_meta` by exactly one for the set — organization changes never bump `archive_revision` (organization is not archive content). Stable-key preview matching extracts the case-folded address from author strings (`Name <address>` and bare-address forms); display-name-only chat authors never match a stable-key anchor.
- **Persistence.** People and links live in `vault.db`, so they survive restart and ride backup/restore with the vault (subject to the same schema ceiling as everything else); they never enter the sample/demo archive.

**Proposed** (later slices): candidate identity listing, the person-scoped message query (timeline with a stable cursor and an explicit unknown-dates section), Tauri commands over the storage API, and the linking-flow and person-view UI.

## Time semantics

**Current** (storage and v2 search). Every message keeps the original timestamp text, the resolved UTC instant (`sent_instant`, NULL when unknown), the zone it was interpreted in, and a confidence label (`explicit_offset`, `user_confirmed`, `legacy_assumed`, `unresolved`, `missing`). Mail `Date` offsets, Telegram/Signal Unix epochs, and Telegram's naive `date`-string fallback (an exporter-UTC stamp, stored verbatim) resolve directly as `explicit_offset`. WhatsApp/Telegram-style naive local stamps resolve DST-aware in the machine's IANA zone: ambiguous fold times take the first occurrence, and gap wall-times stay `unresolved` with their original text preserved. Legacy pre-canonical values keep their text and carry `legacy_assumed`; migration 7 additionally resolves legacy WhatsApp blind-Z stamps to their machine-zone instants and re-keys the affected identities, without changing what the text says. Corrections are explicit, never a migration side effect; the `user_confirmed` label (**proposed**, M3.3 import confirmation) exists in the schema for user-verified interpretations.

v2 search interprets day bounds in an explicit validated IANA timezone (empty = OS default): `from_date` is the local midnight of the from-day and `to_date` the exclusive local midnight of the following day, covering 23/25-hour DST days correctly; reversed bounds are rejected. Unresolved/missing instants are excluded from bounded searches and sort deterministically after dated messages (by ID) in unbounded browse. Paged results carry the `archive_revision` so the UI can offer refresh instead of silently restarting pagination. **Proposed**: persisting the workspace timezone as a setting and surfacing time-confidence indicators throughout the workspace UI.

## Migration and recovery

**Current.** The versioned ledger applies numbered migrations inside the safe-migration path below (never edit an applied version — add a new one). Relevant steps: 1–3 legacy schema (`messages`, `messages_fts`, `imap_sync_state`, embeddings); **4** canonical store — every legacy row copied with IDs unchanged into `source_instances` / `conversations` / `archive_messages` / `message_identities` / `message_occurrences` / `sync_checkpoints`, one unresolved legacy source instance per legacy namespace (including IMAP namespaces — a host is never invented from a username), one legacy-unresolved conversation per legacy chat group, an alias identity per legacy `(source, external_id)`, one `legacy-import` occurrence per message, embeddings re-bound to canonical IDs; 5 watched folders; 6 statistics counters; **7** conversation-key backfill — Telegram/Signal conversations re-group by the external-id chat prefix (merging renamed imports, splitting same-name chats), WhatsApp conversations derive the content key and every WhatsApp identity re-keys to the current hash formula so post-upgrade re-imports dedup, and unsafe shapes (id-less exports, author-less WhatsApp, pre-M1.3 mail without threading headers) stay `legacy_unresolved`; **8** durable source instances (connector key, state, attempt/success stamps); **9** IMAP failed-item ledger plus the per-source exclusion flag (M2.3); **10** bounded-import recovery — `import_checkpoints` and `import_issues` (M2.2); **11** the persisted `sync_schedule` singleton (M2.4); **12** is M3.2-era (`archive_meta`'s `archive_revision` counter and `message_occurrences.import_id`); **13** is M4.2-era (the `media_objects` unlinked-file registry, landed with #60 ahead of its acceptance record); **14** is the account-level sync error state (`source_instances.last_error_class/last_error/at` — the restart-durable record of what fell and why, cold review §2.2/#5); **15** is the covering index `idx_archive_messages_source_channel` on `archive_messages (source_instance_id, channel)` — each per-source mail-vs-chat channel probe (`Storage::account_channel_flags`, the honest signal behind the source-icon taxonomy and the accounts overview's `medium`) becomes an index seek instead of walking a source's rows; **16** is the finished-jobs ledger `job_ledger` — one appended row per terminal job transition (state, times, one-line result summary, serialized terminal state), pruned to the newest 50 on write, replayed at pool spawn as read-only historical records under synthetic ids so the Activity panel lists a restart's inherited history without ever mistaking it for live, cancellable jobs; **17** drops the single-column index `idx_archive_messages_source` (created by 4 with the canonical store): 15's composite `idx_archive_messages_source_channel (source_instance_id, channel)` covers its leading column, so the redundant index only cost write amplification — no query referenced it by name; **18** is the `saved_searches` table — one row per named saved-search definition (`id`, unique `name`, `request_json`, `created_at`, `updated_at`), where `request_json` holds the serde JSON of a v2 `SearchArchiveRequest` with `limit`/`offset` stripped: the definition is the dynamic query and its complete filter semantics (canonical source ids, author, explicit day bounds plus timezone, attachment/honesty filters, import scope, sort), so reopening re-executes the search — newly imported matching messages appear, and display-label renames or duplicate labels never redirect a saved search. Rename/update/delete are single-row operations on the definition and never touch archived messages. **19** is the collections organization layer (part 1 of the collections slice): `collections` plus `collection_members` referencing canonical messages by stable rowid with no FK on the message side (absent references surface as unavailable memberships), memberships cascading on collection deletion only; **20** adds the `people` and `person_identity_links` tables of the unified-person slice (additive DDL only, no data changes). **21** is the what's-new boot digest's `created_at`-leading composite index on `archive_messages` (`idx_archive_messages_created_source`, second column `source_instance_id` so the per-source count is covered by the index alone) — numbered 21 here because both this slice and the people slice originally claimed 20 and the people slice was first in the merge queue. The M4.1 object store contributed no migration: media references ride `raw_json`, and the store's integrity is reconciled against `media_digests()` rather than a table.

Opening an existing database with pending migrations goes through the safe-migration path ([safe_migration.rs](../crates/vault-core/src/safe_migration.rs)):

1. **Newer-schema refusal** — a database recording a schema version newer than this build is refused before anything on disk is touched.
2. **Capacity preflight** — free space must cover the snapshot (main file + journal sidecars + slack); a refusal leaves the file byte-identical.
3. **Pre-migration snapshot** — the WAL is checkpointed (TRUNCATE) so committed WAL-only rows are folded in, then the file is copied (fsynced temp + atomic rename) to `<db>.pre-migrate-v<from>.snapshot` next to the database.
4. **Transactional conversion** — all pending migrations commit in one single SQLite transaction (all or nothing).
5. **Validation** — `PRAGMA quick_check`, FTS document-count parity over the shadow `_docsize` tables (a `COUNT(*)` on an external-content FTS table would read the content table and hide drift), and the FTS5 integrity-check command, over both `archive_fts` and the frozen legacy `messages_fts`.
6. **Rollback/reopen** — any failure after the snapshot exists closes the connection and restores the original file byte-for-byte from the kept snapshot; the next open retries the conversion on the intact original. A validated conversion deletes the snapshot. A failed *post-conversion validation* additionally records a durable `<db>.migration-failed` marker so later opens refuse with the recorded reason instead of retrying the same deterministic failure forever; recovery is manual by design (fix or restore, then remove the marker).

Failure-injection tests at every stage (before/within/after conversion) prove the original archive is never stranded or modified. Migration preserves all information actually stored, not data the old importer already discarded: folder memberships or originals absent from the old database require resync/reimport, pre-M1.3 mail lacks reply evidence (reimport originals to enrich threads rather than infer), and reimport compatibility checks identity aliases before creating a new canonical record.

## v2 IPC surface

**Mixed.** Use snake_case JSON fields to match Rust serde. Every command returns `Result<T, AppError>`; job start commands return `{job_id}` immediately. ### Search request and response

**Current** (M3.2; [search2.rs](../crates/vault-core/src/search2.rs) is the source of truth).

```typescript
type SearchArchiveRequest = {
  text: string;
  source_ids: string[];       // empty = all
  conversation_id?: string;
  import_job_id?: string;
  author: string;             // Unicode case-folded substring
  from_date?: string;         // YYYY-MM-DD in timezone below
  to_date?: string;
  timezone: string;           // validated IANA identifier
  has_attachment?: boolean;
  time_assumed?: boolean;     // true = legacy_assumed/unresolved/missing,
                              // false = explicit_offset/user_confirmed
  grouping_unverified?: boolean;  // true = no conversation or
                                  // legacy_unresolved; false = verified/user_linked
  files_missing?: boolean;    // true = references without preserved bytes,
                              // false = every reference preserved (or none)
  sort: "relevance" | "newest";
  limit: number;              // default 50, clamp 1..200
  offset: number;             // clamp 0..1,000,000; ignored when cursor is set
  cursor?: string | null;     // opaque keyset cursor from next_cursor
};
type MessageSummary = {
  id: number;
  source_id: string;
  source_label: string;
  conversation_id: string | null;
  conversation_label: string | null;
  author: string;
  subject: string | null;
  sent_at: string | null;     // resolved UTC instant only
  time_confidence: "explicit_offset" | "user_confirmed" |
    "legacy_assumed" | "unresolved" | "missing";
  snippet: string;            // bounded: 500 Unicode characters including hit
                             // markers for text search; a 240-character body
                             // prefix when browsing
  attachment_count: number;
  available_attachment_count: number;
  has_conflicting_revision: boolean;
};
type SearchArchivePage = {
  hits: MessageSummary[];     // ID, source/conversation labels, metadata, snippet
  total: number;
  limit: number;
  offset: number;             // the request's offset; 0 for cursor pages
  archive_revision: number;  // changes whenever a committed batch changes results
  next_cursor: string | null; // keyset cursor to the next page; null at the end
};
```

Normalize free text using the safe term builder; keep all SQL values bound. Limit text to 2000 Unicode characters and reject invalid dates/reversed bounds. Empty text browses newest regardless of requested relevance sort. Text relevance sorts by weighted FTS5 `bm25()` — BM25F column weights with the subject boosted over body and author — then by ID; newest sorts by resolved instant descending then ID descending, unresolved dates last. Counts and rows come from one read snapshot. Page grouping must not change this order. If the archive changes, report its revision and let the UI offer refresh; do not silently restart pagination. The honesty filters `time_assumed`, `grouping_unverified`, and `files_missing` are tri-state like `has_attachment` (absent/null = no filter; `true` keeps the uncertain rows, `false` their complement) and conjunctive with every other filter; all three are WHERE clauses over existing columns, with no schema change.

**Current (keyset cursors for deep pages).** Every page also returns a `next_cursor` — the last row's sort position (sort key plus message id, and the order mode it was issued under) as an opaque base64 string — whenever a following page exists, and `null` at the end of the result set. Sending it back as the request's `cursor` starts the next page strictly after that position through a keyset WHERE clause (compound sort-key/ID comparison over bound parameters, following the `conversation_context_v2` cursor precedent), so a deep page costs the same as the first page instead of degrading linearly with `offset`. Contract: a cursor is bound to the order mode it was issued under (browse = empty text, `newest` = text sorted newest, `relevance`); a cursor from a different mode is rejected with `invalid_input`, as is any malformed cursor — never silently ignored. When both `cursor` and `offset` are sent the cursor wins (the page reports `offset: 0`; the continuation is the cursor itself). The deterministic orderings are unchanged (relevance = bm25 then ascending id, newest = instant descending then id descending with unknown instants last — the newest/browse cursor carries the unknown-instant flag so the compound predicate holds across the NULL boundary; the relevance cursor carries the bm25 rank and survives tied scores through the id tiebreak). Totals are still the exact whole-filtered-set count computed in the page's one read snapshot with the archive revision; same archive revision plus same cursor always yields the same page, and across a revision change the cursor stays usable while the existing revision notice governs. The v1 `search_messages` path (`SearchQuery`/`SearchPage` over `search_page`) reads and writes the same wire fields with the same rules, except it has no `newest` text-sort mode (empty text browses, text sorts relevance) and no archive revision. The UI keeps its offset paging; cursor adoption is a follow-up slice.

**Current (M5, consent gate + workspace scope) / proposed (approval flow).** The shipped ask surface is the v1 `llm_ask` command carrying an explicit `consent` flag and an optional `scope` payload: without `consent: true` a network provider selection is downgraded to a fully local ask inside the backend before any provider client is constructed — configured keys and environment fallbacks never cause provider calls by themselves (proven by mock-endpoint tests recording zero wire requests). A consented ask makes exactly two provider round trips, translate (question + date context) then summarize; the summary context is the top `summarize_top` (default 8) results as numbered blocks — `[n] author · sent_at` with the body truncated to 500 Unicode characters — plus the question; no filenames, raw JSON, attachments, or embeddings are sent, and the summary is skipped entirely when there are no results. Answer citations `[n]` map to result `n − 1` of that ask's own returned results — a fixed map, not whichever search results are currently on screen — and markers beyond the summary window or outside the result list stay plain text. The optional `scope` (canonical `source_ids`, `author`, local `from_date`/`to_date` with `timezone`, `import_job_id`, and the tri-state `has_attachment`/`time_assumed`/`grouping_unverified`/`files_missing` honesty filters) is validated against the vault first — an invalid scope fails the ask before any retrieval — and then constrains both retrieval legs by reusing the v2 search predicate SQL: plan-generated date and author constraints intersect with it (later lower bound, earlier upper bound; authors conjunctive), the plan can narrow but never broaden it, an empty date intersection returns no matches without falling back to unscoped retrieval, and only in-scope messages can reach citations or the summary context. Absent/`null` scope asks over the entire archive, so existing callers keep working. **Landed (M5.2 part 1, backend)**: the job-backed prepare/approve/generate flow itself — `prepare_ask_v2` / `generate_answer_v2` in the table above — with the exact payload preview and digest-bound approval, stale-approval invalidation on endpoint/question/filters/result-snapshot changes, cooperative cancellation and progress, and the same scope intersection on the prepare leg (the v1 `llm_ask` stays the shipped frontend surface meanwhile). **Proposed** (the M5.2 remainder): the frontend sending the active filter snapshot with each ask plus the visible scope line with an explicit "Entire archive" state and invalidation of pending results/disclosures when the scope changes (the backend scope is exercised only by tests until that lands), and the part-2 UI wiring of the preview → approve → answer flow (payload preview display, progress, cancel) plus the part-3 v1 `llm_ask` cleanup once every caller and fixture migrates. The persisted off-by-default consent switch that once opened this proposed list is superseded by the 2026-11-16 decision ([#181](https://github.com/acailic/mailchat-vault/issues/181)) — the shipped session-scoped, in-memory-only consent is the decided release behavior (M5.1 closed).

## Errors and events

**Mixed.** The background-job protocol below is **current** (M2.1); the `AppError` envelope is **current for the v2 reading surface** (M3.2 ships the struct — `code`, safe `message`, optional `field`, `retryable`, optional `job_id` — with the codes `invalid_input`, `not_found`, and `internal`, mapping query-shape faults to `invalid_input` and date faults to the `from_date/to_date` field); the fuller code list and richer job states remain **proposed** for their owning slices.

**Current job protocol.** Jobs carry stable ids and typed states — `queued → running → succeeded | failed | cancelled` — with typed error kinds (`storage`, `io`, `import`, `network`, `cancelled`, `queue_full`, `invalid`, `internal`) instead of bare strings. Cancellation is cooperative and may wait for the current bounded item/batch; the UI must not promise instantaneous cancellation. No automatic retry for authentication failure (a source without credentials is reported, not retried); network failures retry on user action or the next scheduled round, never in an immediate storm. The shipped wire names are `job_submit` / `job_get` / `job_list` / `job_events_since` / `job_cancel` plus the `job-event` window event: each event is `{seq, at, job, type, …}` stamped from one global monotonic counter. Events are hints; a client that missed some (webview reload, dropped event) recovers by polling `job_events_since(cursor)`, which returns the gap, the newest `seq`, a `trimmed` flag when the bounded ring no longer holds part of the gap, and the current records to reconcile from. Progress carries done/total with unknown totals as zero, never guessed percentages. Job records live in the process registry with a bounded finished-job history; after an app restart the registry is empty, and interrupted work resumes through its durable records (checkpoints, ledgers) rather than persisted job rows.

**Proposed remainder.** The full `AppError` code set beyond the shipped `invalid_input`/`not_found`/`internal` — `unsupported_format`, `ambiguous_identity`, `credentials_required`, `authentication_failed`, `network_unavailable`, `capacity_exceeded`, `disk_full`, `integrity_failed`, `conflict`, `cancelled`, `unsupported_version` — lands with the slices that can raise it. Never expose raw server responses containing credentials or filesystem internals by default. Not yet implemented: the `partial` and `interrupted` states (a partial outcome is reported inside the succeeded job's result summary and issue ledgers today), a distinct `cancelling` state, retry as a linked job that never rewrites the original outcome, per-item outcome counters (`processed = new + existing + failed + service_skipped`) — media item counters are current in import summaries (`referenced`/`stored`/`deduped`/`missing`/`linked`, M4.1, plus the unlinked honesty counters `unlinked`/`unlinked_deduped`/`unlinked_dropped`/`unlinked_walk_failed`), byte counters are not — and `vault_job_v2` as the event name.

## Media and capacity

**Mixed.** The M4.1 half is **current**: every media copy runs through the store's stage→promote→reference lifecycle under two enforced budgets — a per-import media `Capacity` (32 GiB of new object bytes, 100,000 new objects per run; duplicates refunded, so re-imports of preserved media cost nothing) and per-tree `ImportBounds` for every directory walk or ZIP expansion (20,000 files, 32 GiB total bytes, depth 6; traversal and symlink escapes refused; declared ZIP sizes preflighted and actual streamed bytes re-checked; nothing of a rejected archive kept). Tree-level violations refuse the import with a typed bounds error before messages are stored; an unreadable or individually budget-refused file lands in the import summary's missing count instead of aborting committed work — visible partial results, never silently skipped trees. Users cannot yet raise limits in a preview UI; the free-space estimate and configurable limits belong to the import preview (M3.3) and M4.2 surfaces. Both import commands share one outcome shape: `import_mbox` returns the chat import's `{summary, import_id, media}` (the mail pass's attachment counters; the mail pass runs no unlinked tree walk, so its unlinked legs stay zero), and the import status line renders the media counters only-non-zero — stray-file storage (`N unlinked`), budget drops (`N dropped (budget)`), and a failed tree walk (`walk failed`) surface instead of being swallowed. Finding resolution is **current** and read-only: `Storage::media_digest_references` resolves one digest to every archived message referencing it (message id plus conversation/date context and the reference's display name, one bounded page-with-limit plus a total, mirroring the search surface's clamps), so the `media_reconcile_detail` command turns each missing/corrupt finding into affected messages to open and — for digests in the `media_objects` unlinked registry — the known import that stored them; orphan/staging/foreign findings stay categories of their own, never masquerading as message failures.

**Proposed** (M4.2/M4.4 — the M4.3 media display surface landed with #58 and its acceptance record stays open with the milestone): explicit availability per reference (`available`, `missing`, `unsupported`, or `failed`; unsupported preview does not mean unpreserved bytes — `available` with `preview_supported=false` when copied successfully; `unsupported` means the importer cannot preserve the referenced item, with an explicit issue explaining why) and roles (`attachment`, `inline`, `original`, `unlinked`). Per-file safeguards beyond the run budget (e.g. a 2 GiB individual-file cap), configurable limit raising, ZIP-entry-count and expansion-ratio caps beyond the byte bound, and the 1 GiB free-space reserve with import/backup preflight remain design for their owning slices, as do per-file naming of what was not preserved beyond the summary counts and backup of object bytes (M4.4). Deleting a message removes references, not objects still used elsewhere or pinned by retained recovery manifests. Text records larger than 8 MiB normalized text are preserved as originals and reported for explicit import override; do not truncate archived content to satisfy batching limits. These defaults require large-file fixtures, not giant committed binaries.
