## Execution rules

- Read the [product requirements](product-plan.md#functional-requirements), [UX contract](ux-specification.md), [data/API contract](data-and-api-contracts.md), and [validation matrix](validation-and-release.md#acceptance-scenarios) before implementing the affected slice.
- Keep changes focused on the named slice. Preserve current test coverage while updating assertions for intentional behavior changes; do not delete tests because the new design exposes failures.
- Implement v2 IPC alongside v1 until callers migrate. Do not leave commands writing different canonical stores. Exercise legacy upgrade paths with disposable fixtures.
- Each completion record includes revision, changed behaviors, tests run, failures/limitations, migration/recovery evidence, and remaining work. Mark checkboxes complete only with that evidence.
- Never test migrations, deletion, restore, or imports against a user's personal vault. Use isolated app data roots and synthetic fixtures.

### M2 completion record (2026-11-05, M2 code complete at `57f40c8`, spec tree at `1115eac`)

**Revisions.** M2.1 database pool + background job engine — writer worker, two read connections, per-connection initialization, bounded write/job queues, typed job states/errors, event log with monotonic sequence and polling recovery, v2 `job_*` commands and `job-event` window events — #40 (`00ed975`). M2.2 bounded streaming ingest — parser interfaces yielding one item at a time, batched commits with issue records, cooperative cancellation, checkpoint restart recovery, bounded media pass — #42 (`fbdf964`). M2.3 IMAP coordinator — rounds over every configured non-excluded source, fetch outside storage ownership, atomic occurrence/checkpoint/ledger commits, durable failed-item accounting, UIDVALIDITY epoch resets, per-source exclusion — #41 (`0dc393e`). M2.4 opt-in job-backed scheduler plus the real-path performance harness (paginated search, IPC-shaped round trips, concurrent ingest, pool startup) — #43 (`84895d9`), with the interval-preservation/status-normalization fix #50 (`57f40c8`).

**Changed behaviors.** The archive is no longer served through one guarded connection: every command and job reads and writes through the pool (writer thread + two read connections + job runner), and network/parsing waits happen on job threads with no connection held — a stalled IMAP fetch blocks neither searches nor writes (proven at single-account and coordinator-round scale). All production imports run the bounded streaming path (at most 200 items or 8 MiB of body text per atomic batch commit, issue records and checkpoint advance in the same transaction, media extraction on the driver thread before commit); the whole-archive `collect` helpers remain only for small parser tests. Cancellation is cooperative per item and discards only the uncommitted partial batch: committed data and reported counts always agree, and a cancelled or interrupted import resumes from its committed position without duplicates or lost failures (import identity is path + length + mtime, so an edited file is a new import, never a shifted resume). IMAP sync commits message rows, occurrences, failed-item ledger rows, and the checkpoint in one transaction per fetch batch (≤50 messages); items that cannot be stored are ledgered with fixed reasons and retried every round until they resolve, and a UIDVALIDITY reset rescans and dedups while clearing the abandoned epoch's ledger rows. Coordinator rounds skip excluded sources, report sources without credentials instead of erroring, and never let one failing source sink the round. The periodic scheduler is opt-in (off by default, 15-minute default interval clamped to 1 minute–24 hours), persisted in the vault, submits rounds as ordinary `imap_sync_all` jobs, never overlaps rounds, and collapses sleep/resume/offline gaps into exactly one catch-up round. The performance harness now times the real paginated query path (FTS5 MATCH + filters + LIMIT/OFFSET + COUNT + snippets) with per-query p95 CI budgets, and the historical `search_filtered` tables are preserved verbatim below the current results.

**Tests run (2026-11-05, this machine, `cargo test -p vault-core`).** `--test jobs` 13 passed — search completes while writes are in progress, two readers run concurrently, the write queue backpressures and keeps submission order, typed job lifecycle/cancellation/progress, event sequences are monotonic and recoverable by polling including ring trimming, queue-full refusal without waiting, and the IMAP network-stall-does-not-block-writes-or-reads proof over the pool; pool sync matches direct sync archive-for-archive; events serialize flat for the frontend. `--test bounded_ingest` 21 passed, 1 ignored — stream/collect parity per format with skip determinism, both batch limits honored, issue records durable with positions and idempotent across reruns, cancellation preserves committed data and counts, cancelled runs resume and complete without duplicates, restart recovers from the last committed position, the bounded import runs through the pool, and the driver never holds more than one batch; the ignored heavy test `large_generated_input_stays_within_memory_budget` was run separately with `-- --ignored`: **passed** — 153.6 MB Telegram JSON + 137.7 MB WhatsApp text (150k messages each) imported with peak RSS growing 9.1 MB against the suite's 96 MB budget. `--test imap_coordinator` 10 passed — a round syncs every configured source and exclusion skips one, no-credentials is reported (a failing resolver is Failed, not NoCredentials), interruption mid-fetch leaves checkpoint and archive in agreement, a mid-batch storage fault rolls back the whole batch, checkpoint recovery works across a pool restart, a missing fetch is ledgered and heals next round, an unreachable source fails alone, and searches and writes complete while a round is parked on the network. `--test scheduler` 12 passed — schedule defaults off at 15 minutes, persists and survives reopen, clamps to configured bounds, a persisted out-of-bounds interval arms normalized (#50), rounds fire per interval as plain jobs, a round outlasting the interval neither overlaps nor queues, a clock-jump gap collapses to one catch-up round, disabling cancels the active round, failed rounds keep the cadence, and status publishes transitions. `--test imap_sync` 14 passed — the batch machinery under the coordinator against the mock IMAP server: durable instances, multi-folder occurrences, conflicting revisions flagged, atomic fetch-batch commits with mid-batch fault rollback, failed-item ledger accounting including retry/resolution and UIDVALIDITY-reset clearing, durable across reopen.

**Acceptance mapping.** A05 (slow network while searching, cancel and restart at batch boundaries): the network-stall proofs in `jobs` and `imap_coordinator` plus the cancellation/resume/restart tests in `bounded_ingest`; readers never waited behind a write in the concurrent-ingest measurements ([BASELINE.md](../tests/perf/BASELINE.md)); concurrent imports are bounded by the single runner thread (imports serialize, reads continue). A06 (missing UID/body, parse failure, transport disconnect, per-folder error, cursor commit failure): the `imap_sync` ledger/rollback suites and `imap_coordinator`'s missing-fetch, interruption, and mid-batch-fault regressions, plus durable `import_issues` in `bounded_ingest`. A11 (large datasets, query while ingesting, deep pages, broad common terms, bounded memory): [BASELINE.md](../tests/perf/BASELINE.md) M2.4 records — p50/p95/p99 for ten query shapes at 100k and 1M (including deep FTS/browse pages, rare-selectivity terms, and the ubiquitous worst case), IPC-shaped round trips with serialization, search-while-ingesting at 100k/1M, startup including `DbPool::spawn`, and the heavy memory-budget proof above; a literal zero-hit query was not separately profiled (no-match behavior is covered by the correctness suites, and an empty FTS result is the cheapest shape by construction).

**Migration/recovery evidence.** Migrations 9–11 are additive (failed-item ledger + exclusion flag; `import_checkpoints`/`import_issues`; the `sync_schedule` singleton) and apply through the M1.4 safe-migration path (snapshot, preflight, single-transaction conversion, validation, rollback) — no existing vault data is rewritten. Interruption injections at every batch boundary: a dead connection mid-fetch leaves the cursor at the boundary of durably stored work; an injected mid-batch storage fault rolls back the entire batch with the cursor unmoved; a pool restart mid-import resumes from the committed checkpoint without duplicates; cancellation mid-import preserves committed rows and counts and the resumed run completes cleanly; completed reruns neither duplicate messages nor issue records.

**Failures/limitations.** Job records live in the process registry, not a database table: no `interrupted`/`partial` states, no linked retry jobs, no per-item outcome counters in events — job history does not survive an app restart (the jobs panel starts empty), and resumability is carried by the durable checkpoints/ledgers instead. All background jobs serialize on one runner thread (stricter than the proposed "at most two ingest jobs"; the only per-source admission control is the IMAP exclusion flag). The connection busy timeout is 5 seconds, not the 2 seconds sketched in the proposal. Cancellation is cooperative and bounded by the current item, batch, or socket call; no cancellation-latency measurement was recorded, so the 200 ms acknowledgment target remains unmeasured. The scheduler drives IMAP rounds only (watched folders and embeddings have no schedule). Performance was measured on the paginated `search_page` path plus serialization — the v2 command surface (`search_archive_v2`) and the webview/OS hop are not separately measured, the stalled-network search target (≤ 2× idle p95 + 100 ms) was proven qualitatively (non-blocking) rather than timed, and 1M results are informational. Frontend and E2E suites were not rerun for this documentation change.

**Remaining work.** Deferred: a persisted job-record ledger with `interrupted`/`partial` states and linked retries (revisit when a jobs panel needs cross-restart history — a product call, not a correctness gap); keyset pagination for deep pages (recorded as an observation in BASELINE.md); v2-path and end-to-end display timing and the proposed targets table's desktop measurements (F10 remainder); scheduled non-IMAP job kinds if the product wants them.

### M4.4 completion record (2026-11-07, code at `4316541`, the review-gate fix-round commit that includes the fixes through `8ad53b4` and the interrupted-return rollback fix; PR #67)

**Revisions.** vault-core `backup` module (new, [backup.rs](../crates/vault-core/src/backup.rs)) + small storage/object-store surfaces (`Storage::connection` for the writer-side snapshot, `Storage::vault_fingerprint`/`VaultFingerprint`, crate-level digest/fingerprint helpers over arbitrary connections, `SUPPORTED_SCHEMA_VERSION`, `ObjectStore::object_name`), the `Error::Backup` kind, and the `rusqlite` `backup` feature. Frontend: Settings → Storage & backup (create backup, staged validate→commit restore flow, previous-vault list with return/forget) over new pure helpers in [backupview.ts](../src/backupview.ts).

**Changed behaviors.** A backup is one versioned `.mcbackup` ZIP64 container: `manifest.json` (written **last**, holding every entry's path/size/SHA-256, format + schema versions, and source counts), a consistent SQLite snapshot taken through SQLite's **backup API** on the writer connection (new writes pause behind the write queue; the referenced digests are read **from the snapshot**, so writes landing afterwards can neither add nor drop content), the settings file when present (it never carries key material), and every referenced media object — message media entries plus the M4.2 unlinked registry — stored byte-exact. The container is verified (every entry re-read and re-hashed against the manifest) before its temp file is renamed into place; any failure removes only the incomplete backup. Restoring never touches the active vault first: the container is re-checksummed and its database validated (integrity_check, foreign_key_check, schema ceiling, settings version, manifest-vs-db count agreement, object presence) in a staging vault under the sibling `<data>-recovery` directory, producing a preview bound to the staged bytes and the live vault's fingerprint. Committing re-verifies the staged bytes, refuses a vault that changed since the preview, then stops the scheduler and pool and replaces the vault payload (`vault.db`, `settings.json`, `media/`) through a **two-phase switch journal**: journal `switching` (current vault moved aside) recovers by rollback, journal `staged` (new vault moving in) by roll-forward — an interrupted switch always ends at one verified whole vault, resolved automatically at startup before anything opens the vault. The replaced vault is kept as a `previous-<stamp>` slot, never auto-deleted: it can be returned to through the same journaled switch (`return_to_previous_vault`) or forgotten explicitly (`recovery_forget`, refused while a journal is unresolved). Credentials are never backed up or restored — the keyring is untouched — and the restore outcome counts the restored accounts whose `user@host` credentials are missing from this machine's keyring (0 on a same-machine restore whose keyring still holds them), so the UI demands reconnection only where it is real. A successful restore/return requires an app restart (the pool is shut down by the switch; the UI states it and disables further vault actions); every commit-time refusal is raised read-only first (`verify_committable` / `verify_returnable`), so a refused commit never leaves the app's drained pool behind a usable UI. The two switch entry points are serialized behind a switch gate together with `recovery_forget` and the `backup_create` / `restore_preview` jobs (a concurrent switch, forget, backup, or staging refuses fast with the app fully usable; a vanished switch source aborts the switch loudly instead of completing it vault-less), post-drain failures carry the stable `switch_stopped:` token the frontend locks on, while a switch is in flight the UI disables every vault-replacing entry point, staging extraction is bounded by each entry's manifest-declared size (a crafted container cannot expand past its declared budget), a failed startup switch recovery fails closed (the app refuses to open the vault rather than risk a fresh empty database whose writes a later rollback would discard), and the recovery headline claims a committable staged preview only inside the session that validated it — previews are session-bound by contract, so an earlier session's staged bytes are reported as "validate again to commit".
